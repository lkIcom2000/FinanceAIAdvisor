## Intent

**Problem:** Personas exist only as logins with a placeholder clock (`2026-10-20` / `pre-fixtures`, retro item A3). There is no bank data, so no Core function, journey or Scenario can run on realistic, unambiguous persona data (FR-51).

**Approach:** Add the `bank` module (five tables, `BankReadPort.snapshot`, `BankPort`), seven seeded JSON fixtures in `data/personas/` generated by a fixed-seed generator and validated against `data/personas/schema.json`, and one fixture-load path used both at startup (fresh install) and by persona reset. The persona's start date and `fixtureVersion` (SHA-256 content hash) come from its fixture, replacing the placeholder.

## Boundaries & Constraints

**Always:**
- Fixture JSON is the single source for bank rows, `simulated_date` and `fixture_version`. `fixtureVersion` = lowercase hex SHA-256 of the fixture file bytes after CRLF→LF normalisation (64 chars, fits `persona_state.fixture_version`).
- Every fixture validates against `schema.json` (JSON Schema 2020-12, `networknt json-schema-validator` 3.0.8, Jackson 3) when loaded; an invalid, missing or extra fixture stops startup. Fixture `personaId` equals the file stem; each of the seven V2 personas has exactly one fixture.
- Generator: deterministic from per-persona seeds (`L64X128MixRandom`); a test regenerates all fixtures in memory and asserts byte equality with the committed files (`-Dfine.fixtures.write=true` rewrites them).
- Every transaction has a `category` from a closed enum; amounts are decimal strings, scale 2; ids are UUIDs derived deterministically (`UUID.nameUUIDFromBytes`).
- Bank tables: `NUMERIC(14,2)` money, `persona_id VARCHAR(64)` without FK to `personas` (AD-12), FKs inside the module only; registered in `PersonaOwnedTablesTest.OWNERS` and reset by `bank`'s `PersonaResettable` (`bank` already in `RESET_ORDER`).
- Startup seeding and reset share one path: for a persona, every registered owner runs `reset(personaId)` in `RESET_ORDER` inside one transaction. At startup this runs only for personas whose stored `fixture_version` differs from the fixture's.
- AD-21: the transaction starts in a `*UseCase`; owner `reset` and `BankPort` writes are `MANDATORY` on the method.
- `snapshot(personaId, asOf)` returns only data dated ≤ `asOf`; account balances are computed as opening balance + transactions ≤ `asOf`.

**Never:**
- Do not edit V1–V4. No `Instant.now()`/`LocalDate.now()` in domain or application code. No randomness without a seed.
- No Core functions (forecast etc. are Stories 2.3–2.5); the ground-truth check here is a test-side reference calculation.
- No UI or REST endpoint for bank data in this story; no profile data (profile module, Epic 6).
- No real brand, insurer or bank names, no real IBANs (use `DE00` test-style IBANs).

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Fresh install | Migrated DB, `fixture_version = 'pre-fixtures'` | Startup seeds all seven personas: bank rows from fixtures, `simulated_date`/`fixture_version` from fixtures | No error expected |
| Restart unchanged | Versions match | Nothing re-seeded; researcher-set date and BankPort bookings survive | No error expected |
| Fixture changed | Stored version ≠ file hash | That persona is re-seeded at startup, logged with old/new version | No error expected |
| Invalid fixture | Schema violation / stem ≠ `personaId` / persona without fixture | Startup fails naming file and violation | `IllegalStateException` |
| Snapshot | `asOf` before a booking | Booking excluded; balances as of `asOf` | No error expected |
| BankPort transfer | Account of another persona or amount ≤ 0 | Nothing booked | `IllegalArgumentException` |

## Design Notes

**Fixture shape** (all amounts decimal strings):
`{schemaVersion:1, personaId, description, generator:{seed, generatorVersion}, simulatedDate, accounts[{id,type:CURRENT|OVERNIGHT|DEPOT,name,iban,openingDate,openingBalance}], contracts[{id,coverage,provider,policyNumber,policyholder,insuredRole:POLICYHOLDER|CO_INSURED,premium?,paymentInterval?:MONTHLY|QUARTERLY|ANNUAL,nextDueDate?,debitAccountId?,startDate}], transactions[{id,accountId,bookingDate,amount,category,counterparty,reference,recurrenceId?,contractId?}], holdings[...], savingsPlans[...], plantedGroundTruth[{id,description,date,expectedBalance,premiumOverride?}]}`.
`recurrenceId` marks a monthly standing order/direct debit (same day each month); `contractId` marks a premium debit (projected from the contract, not as monthly recurrence); the rest is variable spending.

**Forecast reference model** (decision; Story 2.3's `CashFlowForecast` median must reproduce it): start = current-account balance at end of `asOf`; for each day after `asOf`: apply recurrences due that day (day clamped to month length), subtract `V / daysInMonth` where V = variable spending per calendar month (mean of the last 3 complete months), then apply contract premiums due that day. Rounded HALF_UP to cents only at the end. Generator makes every complete month's variable total exactly V (partial month pro rata), so any window of complete months gives V; gaps between transactions ≤ 4 days (Data Confidence).

**Calibrations (decisions):**
- Lena, asOf 2026-10-15: salary +2,400 on the 3rd (after the 1 Nov premium, so the debit precedes the next salary credit), rent −850 and ticket −58 on the 1st, mobile −25 on the 20th, electricity −65 on the 5th, streaming −13 on the 12th, standing order −300 to overnight on the 4th, V = 930. Balance 15 Oct = 1,974.00 → 1 Nov: 1,974 − 480 − 25 − 850 − 58 − 31 − 620 = −90.00; with 744: −214.00; fixed-only +421.00.
- p-shortfall, asOf 2026-10-28 (as in the experiments): balance 450.00, salary +2,300 and fixed −1,800 on the 1st, V = 400, car premium 620 due 2026-11-28 → −82.04 (addendum's monthly arithmetic gave −70; the daily model is the reference); fixed-only +330.00.
- Others (asOf 2026-10-15; p-harness 2026-10-20 as in the experiments): Marco income 2,100, expenses 2,000, overnight 300; Jonas own liability (annual) + co-insured on parents' family liability policy (premium null), ETF savings plan 100/month and holding; Petra Riester contract 45/month, child benefit 2 × 259; Tim trainee, income 1,150, surplus ≈ 80; p-harness neutral (current account only, no contracts).
- History starts 2025-07-01 (15–16 months). Opening balances are back-computed from the calibrated balance and must be ≥ 0.
- Startup seeding by version mismatch: changed fixtures re-seed that persona on the next start, so fresh install and reset share one code path. A3 needs no new migration; V3's placeholder is overwritten on first start.
